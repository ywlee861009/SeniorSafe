# 할일-008 낙상 감지 알고리즘 보류 및 재개 조건 정리

## 우선순위

P2

## 문제

가속도 센서 기반 낙상 감지 상태 머신은 구현되어 있지만, 현재 threshold와 시간값은 실제 생활 움직임 기준으로 충분히 검증되지 않았다. 오탐과 미탐 모두 제품 신뢰도에 직접 영향을 주므로 현재 MVP에서는 낙상 감지 제품화를 보류한다.

2026-06-03 현재 Android MVP에는 활동 모니터링과 진단 로그 기반이 추가되어 있지만, 낙상 감지 제품 기능은 일반 앱 흐름에서 제외되어야 한다.

- 현재 저장소의 `android/settings.gradle.kts`에는 `core:fall-detection` 모듈이 포함되어 있지 않다.
- 현재 파일 트리에도 `FallDetectionService` 구현은 확인되지 않는다.
- 낙상 감지 관련 완료 티켓은 과거 피벗 전 기록으로 남아 있다.
- MVP 진단 로그는 `core:diagnostics` 모듈의 Room DB에 저장된다.
- 현재 제품화 대상 서비스는 `core:activity`의 활동 모니터링 foreground service다.

남은 검증 포인트는 알고리즘 자체다. 특히 현재 `STILL_THRESHOLD`는 `magnitude < 3.0` 기준이라, 휴대폰이 바닥에 정지해 있어도 중력값 때문에 실제 정지를 잘못 판단할 수 있다. 정지 판단은 magnitude 절대값이 아니라 9.8 근처 안정성 또는 최근 샘플 변화량/분산 기반으로 재설계해야 한다.

## 현재 MVP 결정

- 낙상 감지는 보호자에게 실제 알림을 보내는 제품 기능에서 제외한다.
- 낙상 감지 관련 화면과 API는 신규 MVP 우선순위에서 제외한다.
- 기존 진단 로그와 서비스 구조는 잠금해제 활동 모니터링 구현에 참고한다.
- 낙상 감지를 다시 켤 때는 별도 검증 티켓과 테스트 데이터가 필요하다.
- 일반 사용자 진입 흐름과 Android 네트워크 계약에서 `fall/*` API 의존성을 제거한다.

## 재개 전 작업 범위

- 휴대폰 위치와 활동별 반복 가능한 수동 테스트 프로토콜 작성.
- 걷기, 앉기, 휴대폰 떨어뜨림, 낙상 시뮬레이션의 가속도 trace 수집.
- 자유낙하, 충격, 정지 threshold 튜닝.
- 감지 후 debounce/cooldown 추가.
- 페어링 전/후 낙상 감지 동작을 정의한다.
- 프로세스 종료나 앱 재시작 이후 서비스 상태와 최근 이벤트 상태 유지 검토.
- MVP Runtime Log로 수집한 trace를 기준으로 threshold와 상태 전이 조건을 조정한다.
- 앱 화면 kill, service 생존, OS/service kill, service restart 케이스별 로그와 UI 상태 동기화를 수동 검증한다.

## 완료 조건

- 낙상 감지가 현재 MVP 범위에서 비활성/숨김 처리되어 있다.
- APK에 포함된 코드와 과거 티켓/문서에만 남은 기록을 명확히 분리하고, dead code 여부를 문서화한다.
- threshold 선택 이유가 테스트 데이터와 함께 문서화된다.
- 주요 오탐 케이스의 기대 동작이 정리된다.
- cooldown 동안 중복 알림이 방지된다.
- 앱 재시작 후에도 서비스 상태를 사용자가 이해할 수 있다.
- Runtime Log 기반으로 최소 걷기/앉기/휴대폰 낙하/낙상 시뮬레이션 trace가 남아 있다.
